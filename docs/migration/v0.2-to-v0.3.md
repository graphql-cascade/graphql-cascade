# Migrating from v0.2 to v0.3

v0.3 implements the specification's error codes. It changes no response shapes; existing code keeps working.

## Error Codes

Errors carry one of the standard codes in `CascadeErrorCode`:

| Category | Codes |
|----------|-------|
| Transient, worth retrying | `TIMEOUT`, `RATE_LIMITED`, `SERVICE_UNAVAILABLE` |
| Caused by the request | `VALIDATION_ERROR`, `NOT_FOUND`, `UNAUTHORIZED`, `FORBIDDEN`, `CONFLICT` |
| Server failures | `TRANSACTION_FAILED`, `INTERNAL_ERROR` |

## Server: Error Helpers

The server's error type is `CascadeErrorInfo`; the name `CascadeError` belongs to the error class the tracker throws. Helpers build errors with the right codes:

```typescript
import {
  conflictError,
  notFoundError,
  rateLimitedError,
  timeoutError,
  validationError,
} from "@graphql-cascade/server";

return builder.buildErrorResponse([validationError("Title is required", "title")]);
```

## Client: Acting on Codes

```typescript
import {
  calculateRetryDelay,
  isAuthError,
  isRetryableError,
  type CascadeError,
} from "@graphql-cascade/client";

function handle(error: CascadeError, attempt: number) {
  if (isRetryableError(error)) {
    return { retryIn: calculateRetryDelay(error, attempt) };
  }
  if (isAuthError(error)) {
    return { redirect: "/login" };
  }
  return { show: error.message };
}
```

The client libraries also retry retryable errors themselves: Apollo's `createCascadeErrorLink` and React Query's `useCascadeMutation`.
